How to Create a Simple Box

A step-by-step guide that builds a real working example — the SWOT Box — and teaches you the rules for branching, code management, and working together.

1. What you'll learn

By the end you'll have added a brand-new SWOT Box that takes any text and asks the AI to produce a SWOT analysis (Strengths, Weaknesses, Opportunities, Threats).

A box is made of three small pieces of code. Add all three and your box appears in the sidebar and works:

#FileWhat it does
1client/src/types.tsTells AI Canva your box exists (name, icon, colour, default prompt)
2client/src/store/boardStore.tsTells AI Canva what to do when Run is pressed
3client/src/components/BoxNode.tsx(optional) How to draw your box's output nicely
Golden rule: a text box needs only files #1 and #2. Most student boxes are text boxes. File #3 is only for fancy visuals (score bars, cards, a viewer).

2. Touchpoint 1 — Register your box in types.ts

Open client/src/types.ts. At the top there's a line listing every box type. Add your box name to that list:

export type BoxType = "idea" | "agent" | "research" | "summarise" | "image" | "documents" | "cartoon" | "slides" | "prd" | "ui" | "stitch" | "handoff" | "alignment" | "decision" | "note" | "label" | "timer" | "checklist" | "custom" | "swot";

Now scroll to the big BOX_TYPES object. After the last entry (custom: {...}), add a comma and your own entry:

swot: {
  label: "SWOT",            // the name shown in the sidebar
  icon: "⚖️",               // the icon shown
  color: "#f59e0b",        // a colour (amber here)
  description: "Analyse any idea and produce a SWOT (Strengths, Weaknesses, Opportunities, Threats).",
  hasAI: true,              // true = it calls the AI on Run
  category: "worker",       // "worker" = processes input (vs "input" = text you type)
  defaultPrompt:
    "Turn the following into a SWOT analysis. Use four sections — Strengths, Weaknesses, Opportunities, Threats — as bullet points under each.\n\nIdea:\n{{input_1}}",
  defaultSystemPrompt:
    "You are a business analyst. Produce a clear, balanced SWOT analysis in Markdown. Be specific and honest about weaknesses.",
  defaultWidth: 320,
  defaultHeight: 320,
},

Stop and check: save and refresh — "SWOT" now appears in the sidebar. Clicking it drops a SWOT box. But pressing Run does nothing yet.

Why this matters for your research: the defaultPrompt and defaultSystemPrompt are where your prompt-engineering lives — the heart of your project's research. A good prompt is a design decision you'll defend in your report.

3. Touchpoint 2 — Make it run in boardStore.ts

Open client/src/store/boardStore.ts. Find the function runBox — the big one with runBox: async (id) => {. Inside there's a chain of if (boxType === "...") checks.

For a simple text box, add one else if branch before the slides check:

} else if (boxType === "swot") {
  // SWOT is just text output — the AI already formatted it as Markdown.
  get().updateBoxData(id, {
    output: result.content,
    status: "done",
    error: undefined,
  });
} else if (boxType === "slides") {

What this does when the user presses Run on your SWOT box:

  1. collects the connected inputs (via fillPromptTemplate),
  2. calls the AI backend with your defaultPrompt + defaultSystemPrompt,
  3. runs this branch, saving the AI's reply as the box's output and marking it done.

No new backend code needed — your box reuses the existing /api/generate (Ollama) endpoint that Research/Summarise already use.

4. Touchpoint 3 (optional) — Custom rendering

If you want to draw your output nicely (e.g. colour-coded SWOT sections), open BoxNode.tsx and add a render case. Plain Markdown already renders — so start simple. Make a plain-text box work first, then decide if it needs fancy visuals for your demo.

5. Testing your box

  1. Run the app: npm run dev — client on localhost:5173.
  2. Add a SWOT box from the sidebar.
  3. Add an Idea box, type an idea in it.
  4. Connect them: drag from the Idea box's right ● to the SWOT box's left ●.
  5. Press Run on the SWOT box.
  6. You should see a SWOT analysis appear.

If there's an error, the red banner tells you what went wrong (common: missing OLLAMA_API_KEY, no input, or the AI returned something empty).

6. Rules for branching, code management & working together

Everyone is adding boxes to the same codebase, so these rules stop you from breaking each other's work.

A. Branching — always work on your own branch

Never write code directly on main. Use a branch named after your box.

# 1. Start from the latest code
git checkout main
git pull

# 2. Create a branch named after your box
git checkout -b feature/swot-box

# 3. Do all your work here
# ... edit types.ts, boardStore.ts, etc. ...

# 4. Save (commit) your work with a clear message
git add client/src/types.ts client/src/store/boardStore.ts
git commit -m "Add SWOT box: types entry + runBox branch"
Naming convention: feature/<box-name> — e.g. feature/swot-box, feature/idea-vetter. Never fix, stuff, or asdf.

B. Commit rules

  • Commit small chunks — one logical change per commit.
  • Clear message: Add SWOT box: types entry, or Fix: SWOT now handles empty input.
  • Commit only the files you meant. Check git status first.
  • Never commit secrets — no .env, no API keys, no passwords.

C. The Pull Request (PR) flow

  1. After committing, push your branch: git push origin <your-branch>
  2. Open a Pull Request from your branch into main.
  3. Someone reviews it (instructor or classmate): does it run? is it clean?
  4. After approval, it gets merged.
Rule: never merge your own PR without a review. Reviewing is part of the learning.

D. The "never break main" rule

  • Always pull before you start.
  • Test before you push. A syntax error can break the whole app.
  • Keep changes small; only touch the files you need.

E. Code style & cleanliness

  • TypeScript, not plain JS — use types in .ts files.
  • Format before commit (Prettier).
  • Comments explain the why, not the what.
  • Name things clearly: swot, swotPrompt — not x, foo, temp.

9. What counts for your research

Your build is only 30%. The research (70%) is in the choices you made:

  • Why this box — what problem does it solve, for whom?
  • Why this prompt — what alternatives did you consider?
  • What are the AI's limits? — is the output genuinely useful, or generic?
  • Ethics — could the box be used misleadingly?
You're ready. Follow Part 2 to add your first box, use Part 6 for branch/PR/clean-code rules, and test with Part 5. When it works, write your research around the choices in Part 9.
